# Aspire Environment Variables - Diagnosis & Workaround

## Problem Identified

When `npm start` runs, the Node process is **NOT receiving the `services__keycloak__https__0` environment variables** that Aspire should be injecting.

### Evidence
- Running `node replace-env-vars.js` manually shows: `[DEBUG] No Keycloak-related env vars found`
- The script correctly falls back to hardcoded default: `https://localhost:8443/realms/sarah-realm`
- But Aspire assigns **dynamic ports** (e.g., `:37305`, `:38099`, `:35929`), which the frontend can't use with a fixed hardcoded value

## Root Cause

Aspire's `.WithReference(keycloak)` may not properly inject environment variables into JavaScript/npm processes the same way it does for .NET applications. The `services__` variables are generated by Aspire's runtime discovery service but may not be passed to child Node/npm processes.

## Diagnostic Commands Added

Three new diagnostic scripts have been added to help debug this:

1. **startup-diagnostics.js** - Runs first, logs env state to `.startup-logs/` directory
   ```bash
   node startup-diagnostics.js
   ```

2. **debug-env.js** - Shows filtered Aspire-related env vars
   ```bash
   node debug-env.js
   ```

3. **replace-env-vars.js** - Now has enhanced logging to show what it discovers

## Testing When Aspire is Running

To test if the issue is with Aspire's env var passing:

1. Start Aspire from VS Code (e.g., F5 to launch Sarah.AppHost)
2. Once Aspire is running and has started the frontend, check the startup logs:
   ```bash
   cat .startup-logs/startup-env-*.json | jq '.servicesEnvVars'
   ```
3. Check if `services__keycloak__https__0` appears in the output

### Expected Output (if working)
```json
{
  "services__keycloak__https__0": "https://localhost:37305",
  "services__keycloak__management__0": "https://localhost:35929"
}
```

### Actual Output (if broken)
```json
{}
```

## Possible Solutions

### Option 1: Use Aspire's Environment Variable API (Recommended)
Modify AppHost to explicitly pass the keycloak endpoint to npm process using a custom launcher script instead of `npm start`.

### Option 2: Hardcode Keycloak Hostname, Use Service Discovery
Since Keycloak runs as a named service in Aspire, it might be resolvable by hostname:
- Docker network name: likely `sarah` or similar
- Try: `https://keycloak:8443/realms/sarah-realm` when running in containers

### Option 3: Use .env File Generation
Have a pre-startup script generate a `.env` file based on Aspire's resource endpoints (if accessible).

### Option 4: Update Frontend Configuration
Instead of trying to dynamically resolve Keycloak in npm scripts, make the frontend's OIDC config in auth.service.ts adaptable at runtime (injected into window globals, etc.).
